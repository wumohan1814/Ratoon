# README 与发布（阶段③ · 第 2 步）

> **触发**：用户说"要上线 / 要开源 / 想给别人用"，或做完了准备交付。
> **数据源**：**不新造数据**——README 的内容全部来自已有的根文件（铁律 2）。

---

## 一、README 的六段结构（**顺序不能乱**）

| 序 | 段 | 写什么 | 数据源 |
|---|---|---|---|
| 1 | **一句话** | 这是什么、给谁用 | `00_根/入口.md`「这是什么」 |
| 2 | **为什么做** | 起因 + 想解决的真问题 | `00_根/入口.md`「为什么做」← **阶段① 写的那一段** |
| 3 | **怎么开始** | 最短能跑起来的三步 | `00_根/导航.md` 的启动方式 |
| 4 | **它做到了什么** | 现在能用 / **还不能用**什么（**不许吹**） | `00_根/全貌.md` 的当前形态 |
| 5 | **可信度** | 怎么验证它是真的能跑 | `02` §1「凭」（跑通的证据 / 数字） |
| 6 | **致谢与许可** | 第三方来源 + 本项目自己的许可证 | `00_根/来源.md`；结论出自 `交付前检查.md` |

> **第 4 段是最容易被写成广告的一段。** 破竹的规矩：**写"还不能用什么"，比写"能干什么"更可信**。
> **第 2 段是唯一的"人味"所在**——它是你当初为什么做这件事，**读者只在这段能判断"这跟我有关吗"**。

---

## 二、元数据位清单（**"容易被发现"的实际作用点** · 🔒 公开前才启用）

> **判据**：GitHub 上"被发现"靠**元数据位**，**不靠字数**。
> **写长不增加被看到的机会，反而稀释关键信息。**

| 位 | 填什么 | 为什么是这里 |
|---|---|---|
| **仓库名** | 一眼看懂是什么 | 搜索的第一顺位 |
| **About · description** | 一句话，含最可能被搜的词 | 出现在搜索列表与分享卡片 |
| **topics 标签** | 5–10 个准确的分类词 | **站内分类发现的主要途径** |
| **README 首段前两句** | 一句话 + 给谁用 | 被索引，也是人**决定走不走**的唯一机会 |
| **主语言标签** | 自动 | 分类筛选用 |

> **⛔ 不要为"被搜到"把 README 写长。**
> **破竹自己的 README 就是短的**——这条规则**第一个约束的是破竹自己**。
> 🔒 **本节标为"公开前启用"**：用户已定"先自用验证，成熟后对外"，**现在还没有可发布的东西**。

## 三、致谢段（**可直接粘贴**）

模板在 `交付前检查.md` §1.4。三条硬规矩：

| 规矩 | 说明 |
|---|---|
| **MIT / Apache / CC-BY 来源** | **保留原版权声明**（多数许可要求） |
| **未标注许可证的来源** | 🚫 **只能致谢"思路启发"**，**不能声称"基于其内容"** |
| **本项目自己的许可证** | 末尾一行写清（结论来自 `交付前检查.md` §2） |

**数据从哪来**：项目自己的 → `00_根/来源.md`；破竹自己这个仓库 → `README.md` 的「致谢 / 参考来源」。

## 四、这一阶段的输出（给用户看的）

```
① README 全文（可粘贴 · 分段说明每段来自哪个文件）
② 五个元数据位的建议填写值（🔒 公开前才用）
③ 致谢与许可段落（可粘贴）
④ 一句话：这份 README 里，哪一段是"你本人必须过目"的
```

> **第 ④ 条就是第 2 段（为什么做）**——**它是 Agent 写不出来的那一段**（事实归 Agent，动机归用户）。

## 五、⛔ 边界

- **不优化商业转化**：不写营销话术、不做"种草"、不设计增长路径（`README.md` 的边界）
- **不美化**：第 4 段"做到了什么"以 `全貌.md` 为准，**不写未实现的愿景**
